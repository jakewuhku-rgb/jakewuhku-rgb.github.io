📌 1. Core Stack Boundaries & Addressing

Application Philosophy: Network applications only run on end systems (hosts, servers, mobile devices). Network-core routers and link-layer switches do NOT execute application code, enabling rapid app development and edge-driven innovation.

Socket Interface Demultiplexing

  • Socket: The software interface / "door" between the application-layer process (managed by app developers) and transport-layer infrastructure (managed by OS).
  • Addressing Tuples: Host IP address alone is insufficient because multiple processes run simultaneously. A process is identified by: <IP Address, Port Number>.
Well-Known Ports (0–1023): HTTP (80), HTTPS (443), SMTP (25), DNS (53), FTP (21). Registered: 1024–49151; Dynamic/Ephemeral: > 49151.

🔒 5. Transport Protocols & Layer Boundaries

  • TCP Service: Connection-oriented, 100% reliable byte stream, flow control (receiver buffer protection), congestion control (network overload throttling). Does NOT guarantee timing, minimum throughput, or security.
  • UDP Service: Unreliable, connectionless, no flow/congestion control, minimal protocol overhead. Selected when timely delivery exceeds accuracy needs (DNS, real-time audio).
  • TLS (Transport Layer Security): Implemented at the application layer. Apps link with TLS libraries that wrap cleartext into encrypted sockets before sending down to TCP.

Chapter 1: Principles of Network Applications

Network applications represent the foundational reason for the Internet's existence. Because application code executes exclusively on end systems, developers are unconstrained by core router configurations.

Architectural Paradigms

  • Client-Server Model: Asymmetric design where a dedicated server maintains a fixed, well-known IP address and listens continuously for connections. Clients initiate contact on demand, typically hold dynamic IP addresses, and do not communicate directly with one another. Data centers scale this model to handle enterprise workloads.
  • Peer-to-Peer (P2P) Model: Distributed, symmetric architecture where arbitrary end systems ("peers") communicate directly without central mediation. The fundamental advantage is self-scalability: every downloading peer simultaneously contributes upload bandwidth. The trade-off is management complexity stemming from churn (arbitrary node joins and leaves).

Process Communication & Sockets

Within a single host, processes interact via Operating System IPC (Inter-Process Communication). Across network boundaries, processes exchange discrete messages through Sockets. A socket acts as an application-controlled door to the OS-managed transport protocol stack.

Transport Requirements Spectrum

  • Data Loss Tolerance: Web documents, financial transfers, and emails enforce zero loss (requiring reliable transport like TCP). Multimedia audio/video streaming and interactive voice/games tolerate bounded loss.
  • Timing & Jitter: Interactive voice (VoIP) and real-time multiplayer gaming demand sub-100ms end-to-end latency to remain effective.
  • Throughput: Video streaming mandates continuous minimum bandwidth (e.g., 500 Kbps - 15 Mbps), whereas email and file downloads are "elastic apps" adapting gracefully to available capacity.

Chapter 2: The Web and HTTP

HTTP is the lingua franca of the World Wide Web, designed as a stateless application-layer protocol operating on top of a reliable transport layer (TCP).

Web Document Architecture

A Web page consists of a base HTML document that contains textual structure alongside references to embedded objects (JPEG images, CSS sheets, JavaScript bundles, video files). Each object is globally addressable via a Uniform Resource Locator (URL):

http://www.example.com:80/path/to/myfile.html?key1=value1#section1

HTTP Connection Dynamics: Non-Persistent vs. Persistent

  • HTTP/1.0 (Non-Persistent): Each TCP connection is closed immediately after a single object is transferred. To fetch a web page with 10 referenced images, 11 distinct TCP handshakes must execute sequentially (or via parallel TCP connections), consuming $2 imes ext{RTT} + T_{ ext{transmit}}$ per object and placing heavy connection-state burdens on server OS kernels.
  • HTTP/1.1 (Persistent): The TCP connection remains open after server response. Subsequent requests for referenced objects traverse the established pipe, dropping object download times to as little as $1 imes ext{RTT}$. HTTP/1.1 also introduced pipelining, where clients send requests back-to-back without awaiting immediate responses.

HTTP Message Formats & Status Codes

HTTP/1.1 messages are human-readable ASCII text terminated by (CRLF), with a blank line separating headers from the optional entity body.

  • 200 OK: Request succeeded; requested object encapsulated in body.
  • 301 Moved Permanently: Object relocated; new URL specified in Location: header.
  • 304 Not Modified: Response to Conditional GET; instructs client to render local cache.
  • 400 Bad Request: Request message syntax not understood by server.
  • 404 Not Found: Requested document does not exist on origin host.
  • 505 HTTP Version Not Supported: Server cannot fulfill request with specified protocol version.

State Maintenance: Cookies

Because HTTP servers are fundamentally stateless, stateful sessions (shopping carts, user authentication, tracking) rely on Cookies across four components:

  1. Set-Cookie: ID header in the server's HTTP response.
  2. Cookie: ID header in subsequent HTTP requests from the browser.
  3. A browser-managed cookie file stored on the user's host machine.
  4. A backend database indexing session data by that unique ID.
Privacy Implications: Third-party tracking cookies are injected by third-party advertising scripts (e.g., AdX.com) embedded across distinct publisher sites (e.g., nytimes.com and socks.com), reconstructing cross-site browsing history without explicit user visits to the tracker domain.

Web Caching & Proxy Servers: Worked Numerical Analysis

A Web Cache (Proxy Server) intercepts client HTTP requests. If the requested object is fresh in local cache, it is served immediately; otherwise, the proxy fetches it from the origin server, stores a copy, and returns it to the client.

Lecture Case Study:
  • Access link capacity: $R = 1.54 ext{ Mbps}$, LAN capacity: $1 ext{ Gbps}$.
  • Average object size: $S = 100 ext{ Kbits}$, Client request rate: $\lambda = 15 ext{ requests/sec}$.
  • Data arrival rate to access link: $\lambda imes S = 1.50 ext{ Mbps}$.
  • Baseline access link utilization: $U = rac{1.50}{1.54} pprox 97\%$. Queueing delay explodes into minutes!
  • Option 1 (Hardware Upgrade): Upgrading link to $154 ext{ Mbps}$ drops utilization to $0.97\%$, bringing delay to $pprox 2.01 ext{ s}$, but costs immense recurring ISP fees.
  • Option 2 (Install Local Web Cache with Hit Rate $h = 0.4$):
    • $40\%$ requests served locally in milliseconds.
    • Traffic across access link is reduced to: $(1 - 0.4) imes 1.50 ext{ Mbps} = 0.90 ext{ Mbps}$.
    • New link utilization: $U_{ ext{cache}} = rac{0.90}{1.54} pprox 58\%$, reducing queueing delay to negligible milliseconds.
    • Average End-to-End Delay: $$ ext{Delay}_{ ext{avg}} = 0.6 imes (2.01 ext{ s}) + 0.4 imes (pprox 0.01 ext{ s}) pprox 1.2 ext{ seconds!}$$

Conditional GET

To avoid serving stale content while saving bandwidth, clients issue a Conditional GET containing the header If-modified-since: <date>. If the origin server's file has not changed since that timestamp, it emits a lightweight 304 Not Modified with no entity body, eliminating data transmission delay.

HTTP/2 & HTTP/3 Architectural Breakthroughs

  • HTTP/2: Replaces text parsing with a Binary Framing Layer. A single TCP connection carries multiple interleaved streams, solving Application-Layer Head-of-Line (HOL) blocking. It introduces stream prioritization, server push, and HPACK header compression. However, because all streams share a single TCP connection, a single lost packet at the transport layer forces TCP to stall all streams until retransmission succeeds (TCP HOL blocking).
  • HTTP/3: Completely replaces TCP with QUIC over UDP. Each HTTP stream in QUIC has its own independent stream-level flow control and loss recovery. Packet loss in stream A has zero impact on streams B and C. QUIC integrates TLS 1.3 directly into its initial connection handshake (1-RTT or 0-RTT) and uses 64-bit Connection IDs rather than IP/port tuples, preventing dropped sessions when switching between Wi-Fi and 5G.

Chapter 3: Electronic Mail Systems (SMTP, IMAP, POP3)

Internet email is structured into three primary components: User Agents (UA / mail clients), Mail Servers, and Transfer Protocols.

SMTP Architecture (RFC 5321)

SMTP is a direct, connection-oriented client-push protocol running over TCP port 25. The sending server functions as the client, and the receiving server acts as the server.

  • Three Operational Phases:
    1. Handshaking: Greeting exchange (HELO / EHLO).
    2. Mail Transfer: Envelope declaration (MAIL FROM:<...>), recipient verification (RCPT TO:<...>), and body transfer (DATA).
    3. Closure: Termination sequence (QUIT).
  • Termination Token: The end of message data is signaled by a line with a solitary period: . (CRLF.CRLF).
  • Encoding Restriction: SMTP was engineered strictly for 7-bit ASCII, necessitating MIME (Multipurpose Internet Mail Extensions) encoding for binary attachments and international scripts.

SMTP vs. HTTP Comparison

  • Directionality: HTTP is primarily client pull (browser pulls data from server). SMTP is client push (sending server pushes mail to receiving server).
  • Object Encapsulation: HTTP encapsulates exactly one object per response message. SMTP encapsulates all body components, texts, and attachments within a single multipart message.
  • Commonalities: Both use ASCII commands, human-readable status codes, and persistent TCP connections.

Mail Access Protocols: IMAP vs. POP3 vs. HTTP

A user cannot run an SMTP server on a home laptop to receive email directly because end-user machines are frequently powered off or assigned dynamic IPs. Incoming emails must pool in an always-on mail server mailbox, requiring an Access Protocol for retrieval:

  • POP3 (Post Office Protocol): Download-and-delete model. Simple authorization and retrieval where messages are stored locally on the client and deleted from server, preventing synchronized multi-device reading.
  • IMAP (Internet Mail Access Protocol): State-centric server model. Keeps all messages permanently on the server across hierarchical folders. Tracks read, replied, and flagged statuses identically across multiple clients (smartphones, laptops, tablets).
  • Webmail (HTTP/HTTPS): Modern providers (Gmail, Outlook 365) expose a rich web interface over HTTPS that talks internally to IMAP/SMTP server backends.

Chapter 4: The Domain Name System (DNS)

DNS is an application-layer directory protocol running primarily over UDP port 53. It translates human-friendly alphanumeric hostnames (e.g., www.hku.hk) into routable 32-bit IPv4 or 128-bit IPv6 addresses.

Why Decentralization is Mandatory

A single centralized DNS database would suffer catastrophic single-point-of-failure vulnerabilities, generate insurmountable global query volumes (e.g., Akamai handles >2.2 Trillion DNS queries/day; Comcast handles >600 Billion/day), impose intolerable geographic propagation delays, and make maintenance impossible. DNS scales via a hierarchical, distributed database.

The DNS Server Hierarchy

  1. Root DNS Servers: Contact of last resort. 13 logical root nameservers worldwide, implemented across >2000 physical server instances via Anycast routing, managed by ICANN.
  2. Top-Level Domain (TLD) Servers: Responsible for generic top-level domains (.com, .org, .net, .edu) and country-code top-level domains (.hk, .uk, .cn). Managed by designated registries (e.g., Verisign for .com/.net, Educause for .edu).
  3. Authoritative DNS Servers: Maintained by organizations or managed DNS providers. Houses the canonical hostname-to-IP mappings for an organization's public infrastructure.
  4. Local DNS Servers (Default Resolvers): Maintained by ISPs or public providers (e.g., Google 8.8.8.8, Cloudflare 1.1.1.1). Intercepts client queries, serves cached entries, or queries the global hierarchy on the client's behalf.

Resolution Mechanics: Iterated vs. Recursive

  • Iterated Query: The contacted nameserver replies with the IP address of the next server down the chain ("I do not know the answer, but ask this server next"). The Local DNS Resolver bears the workload of issuing sequential queries down the hierarchy.
  • Recursive Query: The contacted server assumes total responsibility for delivering the final answer, recursively querying subsequent servers itself. This imposes unsustainable memory and connection loads on upper-level Root and TLD servers and is generally disabled at the root level.

DNS Caching & TTL Dynamics

Once a resolver learns a mapping, it stores the Resource Record in memory for the duration of its Time-to-Live (TTL). Caching short-circuits lookups and bypasses root servers for the vast majority of traffic. However, cached records may become temporarily out-of-date if a host IP changes before TTL expiration (best-effort consistency).

DNS Security Threats

  • DDoS Attacks: Bombarding Root or TLD servers with volumetric UDP floods. Historically largely unsuccessful against Root servers due to Anycast filtering and local caching of TLD records.
  • DNS Spoofing / Cache Poisoning: Forging UDP replies with bogus IP mappings before the authentic server responds, tricking the resolver into directing legitimate traffic to malicious servers.
  • DNSSEC (RFC 4033): Cryptographic extensions providing digital signatures, public-key authentication, and data integrity verification for DNS responses.

Chapter 5: Peer-to-Peer (P2P) File Distribution

P2P shifts the burden of content distribution away from expensive server clusters directly onto the consuming clients.

Mathematical Derivation: Client-Server vs. P2P File Distribution

Consider distributing a single file of size $F$ bits to $N$ independent peers. The server possesses upload capacity $u_s$. Each peer $i$ has upload rate $u_i$ and download rate $d_i$, with minimum peer download rate $d_{\min} = \min \{d_i\}$.

Client-Server Lower Bound Derivation:

  • The server must replicate and upload the complete file $N$ times, requiring a server upload time of $ rac{N \cdot F}{u_s}$.
  • The client with the slowest connection requires at least $ rac{F}{d_{\min}}$ time to download its copy.
  • Therefore, distribution time satisfies: $$D_{ ext{c-s}} \ge \max \left\{ rac{N \cdot F}{u_s}, \; rac{F}{d_{\min}} ight\}$$
  • As $N$ grows large, $ rac{N \cdot F}{u_s}$ dominates. The distribution time grows strictly linearly with $N$ ($\mathcal{O}(N)$).

P2P Lower Bound Derivation:

  • The server must upload at least one original copy of the file into the swarm: $ rac{F}{u_s}$.
  • The slowest peer must still download $F$ bits: $ rac{F}{d_{\min}}$.
  • The swarm as an aggregate must download a total of $N \cdot F$ bits. The absolute maximum upload capacity across the entire ecosystem is the server's upload rate plus the sum of all peers' upload rates: $u_s + \sum_{i=1}^N u_i$.
  • Therefore, the P2P distribution time satisfies: $$D_{ ext{P2P}} \ge \max \left\{ rac{F}{u_s}, \; rac{F}{d_{\min}}, \; rac{N \cdot F}{u_s + \sum_{i=1}^N u_i} ight\}$$
  • If all peers upload at rate $u$, the third term becomes $ rac{N \cdot F}{u_s + N \cdot u} = rac{F}{ rac{u_s}{N} + u} pprox rac{F}{u}$ as $N o \infty$. The distribution time approaches an asymptote, demonstrating inherent self-scalability.

BitTorrent Swarm Architecture

  • Chunks: Files are divided into uniform $256 ext{ KB}$ chunks.
  • Swarm & Tracker: A torrent file contains file metadata and tracker addresses. The tracker coordinates peers joining the swarm.
  • Rarest-First Selection: Peers query neighbors to discover chunk distribution and prioritize requesting the rarest chunks first. This maximizes replication speed across the swarm and prevents critical pieces from disappearing if early seeders drop offline.
  • Tit-for-Tat Incentive Engine: Alice measures download rates from all neighbors and uploads exclusively to the top 4 peers sending her data fastest (the remaining peers are "choked"). Top 4 peers are recalculated every 10 seconds. Every 30 seconds, Alice randomly picks one additional peer to "optimistically unchoke", allowing new peers without data to obtain their first chunk and discover higher-speed trading partners.

Chapter 6: Video Streaming & Content Distribution Networks (CDNs)

Video streaming represents over $80\%$ of all residential Internet traffic. Serving millions of concurrent streams requires addressing extreme scale and client link heterogeneity.

Video Compression Basics

Video is a sequence of bitmap frames displayed at fixed frequencies (e.g., 24–60 fps). Raw bitrates are unmanageable without compression:

  • Spatial Redundancy: Compresses redundancy within a single frame (e.g., replacing a sequence of identical purple sky pixels with a run-length representation: (purple, N)).
  • Temporal Redundancy: Compresses redundancy between successive frames. Instead of transmitting frame $i+1$ in its entirety, the encoder transmits only the motion vectors and pixel difference matrix relative to frame $i$.
  • CBR vs. VBR: Constant Bit Rate (fixed bit budget) vs. Variable Bit Rate (bit budget varies dynamically with visual scene complexity and motion).

Dynamic Adaptive Streaming over HTTP (DASH)

DASH solves client diversity by turning streaming control over to the client:

  • Server Partitioning: The video file is chopped into small chunk files (e.g., 2–5 seconds of video). Each chunk is encoded into multiple bitrates/resolutions (e.g., 360p, 720p, 1080p, 4K) and cataloged in a Manifest File (MPD - Media Presentation Description) with matching URLs.
  • Client Intelligence: The client repeatedly samples available server-to-client bandwidth and monitors its local buffer level. If bandwidth drops or the buffer depletes, the client requests a lower-bitrate chunk URL to avoid stalling. When network capacity recovers, it steps back up to higher quality.
  • Playout Buffering: Compensates for network delay variance (jitter). Video rendering begins only after a safety threshold of video frames is buffered locally, decoupling playback timing from packet arrival timing.

CDN Topologies & Operation

  • Enter Deep: Pushes CDN server clusters deep into local ISP access networks worldwide. Akamai operates >240,000 servers in >120 countries, minimizing latency and transit costs by keeping traffic hyper-local.
  • Bring Home: Consolidates servers into fewer, massive server clusters situated at primary Internet Exchange Points (IXPs) near access networks (e.g., Limelight, Fastly).
  • Netflix Infrastructure Model: Netflix hosts account registration, search, recommendation systems, and metadata billing in the Amazon AWS cloud. Video asset rendering and streaming are served from Netflix's custom, distributed Open Connect CDN appliances deployed directly inside partner ISP facilities.

Q1: Should Big Tech companies help fund ISP network infrastructure costs?
Explicit Slides 2–3
Top content providers (Alphabet, Meta, Netflix, Apple, Amazon, Microsoft, Disney+, TikTok) generate over 50% of global internet traffic, with streaming video alone accounting for ~82%. ISPs argue that massive video payloads require immense capital expenditures to upgrade last-mile access links and transit links. Conversely, content providers argue that users already pay ISPs for internet connectivity and that high-quality tech platforms drive consumer broadband demand in the first place, warning that mandatory fees could violate net neutrality and undermine open market competition.
Key Takeaway: Highlights the economic tension between edge content generators driving massive asymmetric downlink traffic and network operators financing physical infrastructure.
Q2: Why does developing applications on end systems enable rapid application development and deployment?
Explicit Slide 4
Network core devices (routers and link-layer switches) execute exclusively up to the network or data link layers; they do not process or understand application-layer protocols. Because edge systems are decoupled from core hardware, developers can write and distribute brand-new network applications instantly without requiring coordination with network operators, firmware updates on intermediate routers, or standardizing protocols within core infrastructure.
Key Takeaway: The End-to-End Principle of the Internet architecture preserves innovation at the edges by keeping network-core routers simple, dumb, and protocol-agnostic.
Q3: Does the IP address of a host suffice for identifying an application process?
Explicit Slide 10
No. A single computer host operates many concurrent network processes (e.g., an Apache Web server, an SSH daemon, a mail server, and multiple browser tabs). The 32-bit IP address identifies only the network interface card on the host machine. To deliver messages to a specific application process, the operating system requires an identifier consisting of both the IP address and a 16-bit Port Number (e.g., 147.8.2.58:443).
Key Takeaway: Demultiplexing to the application layer strictly mandates an <IP, Port> identifier tuple.
Q4: Why does UDP exist when TCP provides full reliability, flow control, and congestion control?
Explicit Slide 14
TCP's guarantees introduce substantial overheads that degrade certain application types:
  1. Connection Setup Delay: TCP enforces a 3-way handshake (1 RTT overhead) before transmitting payload data, whereas UDP sends immediately.
  2. No Head-of-Line Blocking: If a TCP segment is lost, retransmissions stall all subsequent data until the hole is filled. UDP delivers packets independently as they arrive, ideal for real-time voice and gaming.
  3. No Congestion Throttling: TCP reduces sending rate under congestion. Real-time media feeds prefer dropping frames over buffering indefinitely.
  4. Small Header Overhead: UDP uses an 8-byte header versus TCP's minimum 20-byte header.
Key Takeaway: UDP is favored whenever transmission speed, zero setup latency, fine-grained control, or resilience to head-of-line blocking outweighs 100% data reliability.
Q5: Why is maintaining "state" on protocol servers complex and problematic?
Inferred Core Slide 23
Stateless protocols (like base HTTP) require zero memory retention of prior client transactions. When a protocol maintains server-side state, history must be retained across crashes, timeouts, and network failures. If either the server or client experiences a reboot, partition, or crash, their respective views of state diverge and can fall out of synchronization. Reconciling inconsistent distributed states requires complex recovery logic, locking schemes, and database transactions.
Key Takeaway: Stateless design simplifies server architecture, maximizes horizontal scaling, and ensures resilient failure recovery.
Q6: How does a Web browser decide which header lines to include in an HTTP request message?
Explicit Slide 31
A browser constructs headers based on:
  • Browser Specifications & Capabilities: User-Agent communicates OS and browser rendering versions; Accept-Encoding signals supported compression (gzip, brotli).
  • User Configuration & Locale: Accept-Language reflects the user's localized operating system language settings (e.g., en-US).
  • Protocol Standards: HTTP/1.1 requires the Host: header to enable virtual hosting on shared server IPs; Connection: keep-alive requests persistent sockets.
  • Stored Browser State: If a cookie matches the domain path, the browser automatically appends the Cookie: header. If a cached version exists, it injects If-Modified-Since: for conditional validation.
Key Takeaway: HTTP request headers dynamically synthesize client capabilities, protocol requirements, localized environment settings, and cached state.
Q7: Why doesn't a sender's User Agent deliver email directly to the recipient's mail server via SMTP?
Explicit Slide 67
Direct delivery from sender UA to receiver mail server is unreliable because:
  1. If the destination mail server is temporarily unreachable, under maintenance, or congested, the sender's client would be forced to maintain a persistent retry queue, preventing the user from going offline.
  2. Instead, the sender's UA hands off the message to its local mail server via SMTP. The sender's mail server maintains a robust persistent message queue, executing scheduled retries (e.g., every 30 minutes for days) until successfully delivering the email to the recipient's mail server.
Key Takeaway: Intermediate mail servers provide store-and-forward decoupling, guaranteeing persistent message queuing and delivery retry logic.
Q8: Can an email sender track if you have opened or read their email message?
Explicit Slide 67
Yes. Senders achieve email tracking by embedding an invisible $1 imes 1$ transparent image ("tracking pixel") inside HTML emails with a unique query URL parameter (e.g., <img src="https://tracker.com/pixel.gif?user_id=12345">). When the recipient opens the email, their mail client automatically issues an HTTP GET request to fetch the image. The tracking server logs this request along with timestamp, IP address, device user-agent, and user identity.
Key Takeaway: Email open tracking exploits HTML image rendering over HTTP; modern mail clients mitigate this by proxying or blocking external images by default.
Q9: Why can't the Internet function with a single, centralized DNS server?
Explicit Slide 70
A centralized DNS architecture fails on all scalability metrics:
  • Single Point of Failure: If the central database crashes, the entire global Internet ceases to function.
  • Traffic Volume: Global DNS query loads exceed trillions of queries per day (Akamai alone processes >2.2T queries/day). No single server cluster can sustain this packet arrival rate.
  • Geographic Propagation Delay: Queries sent across continents incur massive physical propagation latency.
  • Maintenance & Scale: Centralized record storage for billions of connected devices would be unmaintainable and subject to update bottlenecks.
Key Takeaway: DNS scales by partitioning namespace authority across a globally distributed, cached, hierarchical tree.
Q10: What is Dynamic DNS (DDNS) and what operational challenge does it resolve?
Explicit Slide 84
Traditional DNS assumes that hosts running public services hold static, permanent IP addresses. However, residential ISPs dynamically assign temporary IP addresses to homes and small businesses via DHCP that change periodically. Dynamic DNS (DDNS) solves this by running a client software daemon on the local router or server. Whenever the ISP assigns a new public IP, the DDNS client immediately issues an authenticated update to the authoritative DDNS server, modifying the Type A record in real time with an extremely low TTL.
Key Takeaway: DDNS enables hosting services on networks with dynamic IP allocations by automating real-time DNS record updates.
Q11: Why does BitTorrent use "Rarest First" chunk selection and "Tit-for-Tat" choking?
Inferred Core Slides 94–95
Both algorithms solve fundamental P2P game-theoretic and distribution challenges:
  • Rarest First: Prevents swarm bottlenecking. By replicating the least-common chunks across peers first, the swarm ensures that all pieces remain available even if the original seeder leaves. It also equalizes chunk diversity across peers.
  • Tit-for-Tat: Prevents free-riding ("leeching"). Peers reward contributors by uploading only to the top 4 peers providing the fastest download rates. Optimistic unchoking every 30 seconds ensures new peers without chunks can bootstrap into the swarm and discover higher bandwidth peers.
Key Takeaway: Rarest First guarantees piece survival; Tit-for-Tat aligns individual self-interest with collective swarm performance.
Q12: In DASH, why is adaptation intelligence placed in the client rather than the streaming server?
Explicit Slides 105–106
Shifting adaptation logic to the client maximizes server scalability and optimization:
  • Server Simplicity & Statelessness: Servers remain simple HTTP web servers serving static chunks. They do not track individual client playback buffers, decoding speeds, or instantaneous wireless link changes.
  • Accurate Local Context: The client device is uniquely positioned to measure its own real-time metrics: current screen resolution, battery state, CPU decoding capability, and precise playout buffer occupancy.
  • Server Switching: The client can seamlessly switch to fetch subsequent chunks from alternate CDN cache nodes if an origin link becomes congested.
Key Takeaway: Client-driven DASH preserves server statelessness and places rate adaptation control where buffer and link state are known with highest accuracy.
