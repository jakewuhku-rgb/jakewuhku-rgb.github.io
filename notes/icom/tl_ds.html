Transport Layer: Comprehensive Course Summary

Detailed module breakdown: services, multiplexing, UDP, reliable data transfer principles, TCP mechanics, congestion control algorithms, and modern evolution (QUIC).

1. Transport-Layer Services & Core Principles

The transport layer provides logical communication between application processes residing on distinct end hosts. It sits directly between the application layer (above) and the network layer (below).

1.1 Transport vs. Network Layer (The Fundamental Distinction)

  • Network Layer: Provides logical communication between hosts (end systems identified by IP addresses).
  • Transport Layer: Provides logical communication between processes (identified by transport-layer port numbers). It builds upon and enhances underlying network-layer services.
  • The Household Analogy:
    • Hosts: Houses (e.g., Ann's house and Bill's house).
    • Processes: 12 kids living in each house.
    • Application Messages: Letters enclosed in envelopes.
    • Transport Protocol: Ann and Bill collecting letters from kids, placing them in the mailbox, and distributing arriving mail back to specific kids.
    • Network Protocol: The postal service moving envelopes between houses.

1.2 End-System Transport Actions

  • Sender Actions: Receives raw application messages, divides them into smaller units called segments, populates transport header fields (source/dest ports, sequence numbers, checksums), and hands segments down to the network layer (IP).
  • Receiver Actions: Extracts segments delivered by IP, validates header integrity and checksums, reassembles payload messages, and demultiplexes payload data up to specific sockets.

1.3 Protocol Ecosystem & Ossification

  • TCP (RFC 793, RFC 9293): Connection-oriented, reliable in-order byte stream, congestion control, and flow control.
  • UDP (RFC 768): Connectionless, unreliable, unordered delivery, bare-bones "best-effort" service.
  • SCTP (RFC 4960) & DCCP (RFC 4340): Novel transport protocols designed with multi-streaming and congestion control. Why was their deployment limited? Network middleboxes (firewalls and NATs) drop packets with unrecognized L4 protocol headers.
  • QUIC (RFC 9000): Overcomes protocol ossification by encapsulating modern transport and encryption directly inside UDP in user space.
  • Unsupported Guarantees: Neither standard TCP nor UDP provides delay/latency guarantees or minimum bandwidth guarantees.

2. Multiplexing and Demultiplexing

Multiplexing and demultiplexing allow the operating system to share a single physical network connection among numerous simultaneously running applications.

  • Multiplexing (Sender-side): Gathering data segments from multiple active sockets, appending transport headers, and passing them downwards.
  • Demultiplexing (Receiver-side): Inspecting arriving transport header fields to route segment payloads to the corresponding application socket.

2.1 Demultiplexing Comparison: UDP vs. TCP

2.2 Multi-Layer Protocol Demultiplexing Stack

  • Link Layer Header: Demultiplexes based on Frame Type (e.g., dispatching to ARP, RARP, or IP).
  • IP Header: Demultiplexes based on the 8-bit Protocol ID field: 6 for TCP, 17 for UDP, 33 for DCCP, 132 for SCTP.
  • Transport Header: Demultiplexes based on 16-bit Port Numbers to target application sockets.

3. Connectionless Transport: UDP (RFC 768)

UDP is a minimalist transport protocol that adds almost nothing to IP other than multiplexing/demultiplexing and lightweight error detection.

  • Key Advantages:
    • Zero connection setup latency: No RTT handshakes required before sending data.
    • Statelessness: Sender and receiver do not track connection parameters, sequence states, or buffers, allowing a server to support significantly more active clients.
    • Minimal Header Overhead: Fixed header size of only 8 bytes (vs. 20–60 bytes in TCP).
    • Unthrottled Transmission: No congestion control mechanism; applications can blast packets into the network as fast as desired.
  • Standard Applications: Real-time multimedia/VoIP (loss-tolerant, latency-sensitive), DNS queries, SNMP, and HTTP/3 via QUIC.

3.2 Internet Checksum Calculation

Goal: Detect single-bit and multi-bit corruption (flipped bits) across the transmitted segment.
Sender Procedure:
  1. Treat all 16-bit integers in the UDP header, payload, and an IP pseudo-header as a sequence of words.
  2. Compute the sum using one's complement addition (end-around carry: any carry bit beyond 16 bits is added back to the least significant bit).
  3. Invert all bits of the sum (one's complement) and write this value into the UDP Checksum field.
Receiver Procedure: Add all 16-bit words of the received segment together with the received checksum. If the result is all 1s (0xFFFF), no error is detected; otherwise, an error occurred.

4. Principles of Reliable Data Transfer (RDT)

Reliable data transfer ensures error-free, lossless, in-order delivery over an unreliable physical medium that can corrupt, drop, delay, or reorder packets.

4.1 Stop-and-Wait Protocols & Utilization Bottleneck

In stop-and-wait, the sender transmits a single packet of length $L$ bits at transmission rate $R$ bps, then pauses until receiving an acknowledgment (ACK).

Transmission Delay: $D_{\text{trans}} = \frac{L}{R}$
Sender Link Utilization: $$U_{\text{sender}} = \frac{L / R}{RTT + (L / R)}$$ Example from slides: Link rate $R = 1\text{ Gbps}$, packet $L = 8,000\text{ bits}$, $RTT = 30\text{ ms}$: $$D_{\text{trans}} = \frac{8,000}{10^9} = 0.008\text{ ms} \implies U_{\text{sender}} = \frac{0.008}{30 + 0.008} \approx 0.00027 \; (0.027\%)$$

4.2 Pipelined Protocols

To resolve the low-utilization bottleneck, pipelining allows up to $N$ unacknowledged ("in-flight") packets in the channel simultaneously.

Pipelined Utilization: $$U_{\text{sender}} = \frac{N \cdot (L / R)}{RTT + (L / R)}$$ With window size $N = 3$, link utilization triples to $0.081\%$.

4.3 Go-Back-N (GBN) vs. Selective Repeat (SR)

5. Connection-Oriented Transport: TCP

TCP (RFC 793, 1122, 2018, 5681, 7323, 9293) provides point-to-point, reliable, full-duplex, connection-oriented byte-stream delivery with flow and congestion control.

5.1 Segment Architecture & Key Header Fields

  • Sequence Number (32 bits): Identifies the byte-stream offset of the first data byte in the payload (not the segment number).
  • Acknowledgment Number (32 bits): Identifies the sequence number of the next expected byte from the remote peer (cumulative acknowledgment).
  • Header Length (4 bits): Length of the TCP header in 32-bit (4-byte) words. Standard header = 20 bytes (value 5). Maximum header with options = 60 bytes (value 15).
  • Flags (6+ bits):
    • SYN: Synchronize sequence numbers during connection establishment.
    • ACK: Indicates that the Acknowledgment field is valid.
    • FIN: Sender has finished sending data.
    • RST: Abort/reset an invalid or unresponsive connection.
    • ECE / CWR: Explicit Congestion Notification flags.
  • Receive Window (rwnd, 16 bits): Advertises the number of free buffer bytes available in the receiver's socket buffer (for flow control).

5.2 MTU, MSS & Overhead Calculations

  • MTU (Maximum Transmission Unit): Largest link-layer payload that can be carried in a single physical frame (Ethernet MTU = 1500 bytes; minimum Internet MTU = 576 bytes).
  • MSS (Maximum Segment Size): Maximum quantity of application data carried in a single TCP segment: $$\text{MSS} = \text{MTU} - (\text{IP Header [20B]} + \text{TCP Header [20B]})$$ Default minimum Internet MSS $= 576 - 40 = 536\text{ bytes}$. Typical Ethernet MSS $= 1500 - 40 = 1460\text{ bytes}$.

5.3 Round-Trip Time (RTT) Estimation & Timeout Interval

Karn's Algorithm & Acknowledgment Ambiguity: If a segment is retransmitted, the sender cannot tell whether an arriving ACK corresponds to the initial transmission or the retransmission. Therefore, SampleRTT is measured only for segments transmitted once; retransmitted segments are ignored.
1. Estimated RTT (EWMA with $\alpha = 0.125$): $$\text{EstimatedRTT} = (1 - \alpha) \cdot \text{EstimatedRTT} + \alpha \cdot \text{SampleRTT}$$ 2. Sample Deviation (EWMA with $\beta = 0.25$): $$\text{DevRTT} = (1 - \beta) \cdot \text{DevRTT} + \beta \cdot |\text{SampleRTT} - \text{EstimatedRTT}|$$ 3. Retransmission Timeout Interval: $$\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \cdot \text{DevRTT}$$

5.4 TCP Receiver Delayed ACK Generation (RFC 5681)

  1. In-order segment arrived; all data up to expected sequence already ACKed: Delay ACK up to 500 ms waiting for the next incoming segment.
  2. In-order segment arrived; another segment has ACK pending: Immediately send a single cumulative ACK covering both in-order segments.
  3. Out-of-order segment arrived (gap detected): Immediately send a duplicate ACK indicating the sequence number of the next expected byte.
  4. Arriving segment partially or completely fills gap: Immediately send a cumulative ACK provided the segment starts at the lower edge of the gap.

5.5 Fast Retransmit Mechanism

Waiting for a timeout timer to expire introduces long delays. Because the receiver emits a duplicate ACK for every subsequent out-of-order packet it receives, the receipt of 3 duplicate ACKs (4 identical ACKs total) signals to the sender that a packet was lost. The sender immediately retransmits the missing segment before the timer expires.

5.6 Flow Control vs. Congestion Control

  • Flow Control: Protects a single receiver from having its socket buffer overrun by a fast sender. Sender ensures: $$\text{LastByteSent} - \text{LastByteAcked} \le \text{rwnd}$$ $$\text{rwnd} = \text{RcvBuffer} - [\text{LastByteRcvd} - \text{LastByteRead}]$$
  • Congestion Control: Protects the shared network core (routers and intermediate links) from being overwhelmed by too many senders.

5.7 Connection Lifecycle: Handshake & Teardown

  • 3-Way Handshake (Setup):
    1. Client → Server [SYN]: SYN=1, Seq=x
    2. Server → Client [SYN-ACK]: SYN=1, ACK=1, Seq=y, Ack=x+1
    3. Client → Server [ACK]: ACK=1, Seq=x+1, Ack=y+1 (payload data allowed)
  • 4-Way Connection Teardown:
    1. Client → Server [FIN]: Client sends FIN=1, Seq=x, enters FIN_WAIT_1.
    2. Server → Client [ACK]: Server sends ACK=1, Ack=x+1, enters CLOSE_WAIT. Client enters FIN_WAIT_2.
    3. Server → Client [FIN]: Once done sending data, Server sends FIN=1, Seq=y, enters LAST_ACK.
    4. Client → Server [ACK]: Client sends ACK=1, Ack=y+1, enters TIME_WAIT. Server closes.
  • Why the TIME_WAIT State ($2 \times \text{MSL}$)?
    • Allows the client to resend the final ACK if it is lost, ensuring the server can transition to CLOSED instead of getting stuck in LAST_ACK.
    • Allows all lingering duplicate segments from the connection to expire in the network, preventing them from corrupting future connections reusing the same port numbers.

6. Principles and Costs of Congestion

Congestion occurs when aggregate offered traffic exceeds network link capacities ($\sum \lambda_{\text{in}} > R$).

  • Cost 1 (Queuing Delays): As arrival rate approaches capacity, buffer queuing delays explode toward infinity.
  • Cost 2 (Wasted Retransmissions): Senders must retransmit dropped packets, consuming capacity for re-sent data rather than fresh throughput.
  • Cost 3 (Premature Timeouts & Duplicates): Unneeded retransmissions of delayed but unlost packets further diminish effective throughput.
  • Cost 4 (Upstream Capacity Waste): When a packet traversing multiple hops is dropped downstream, all transmission capacity and buffer space previously used upstream are completely wasted.

6.1 Congestion Control Architectures

  • End-to-End Congestion Control: Network provides no explicit feedback; hosts infer congestion from observed segment drops or increased RTT (standard TCP).
  • Network-Assisted Congestion Control (e.g., ECN): Congested routers mark explicit bits in the IP header (DiffServ/ToS field, ECN=11). The destination echoes this back to the sender by setting the ECE (ECN-Echo) bit in the TCP ACK header.

7. TCP Congestion Control Mechanisms & Algorithms

TCP dynamically regulates its transmission rate using a congestion window (cwnd), ensuring: $$\text{In-Flight Bytes} = \text{LastByteSent} - \text{LastByteAcked} \le \min(\text{cwnd}, \text{rwnd})$$ $$\text{Transmission Rate} \approx \frac{\text{cwnd}}{\text{RTT}} \text{ bytes/sec}$$

7.1 AIMD (Additive Increase, Multiplicative Decrease)

  • Additive Increase: Probes for available bandwidth by increasing cwnd by $1\text{ MSS}$ every RTT until loss is detected.
  • Multiplicative Decrease: Cuts sending rate in half upon loss detected by 3 duplicate ACKs; cuts to $1\text{ MSS}$ on timeout. Produces the iconic sawtooth pattern.

7.2 Phases of TCP Congestion Control

  • 1. Slow Start (SS): Starts at $\text{cwnd} = 1\text{ MSS}$. Window doubles every RTT ($+1\text{ MSS}$ per received ACK), growing exponentially until $\text{cwnd} \ge \text{ssthresh}$.
  • 2. Congestion Avoidance (CA): When $\text{cwnd} \ge \text{ssthresh}$, window grows linearly by $+1\text{ MSS}$ per RTT ($\+ \text{MSS} \times (\text{MSS}/\text{cwnd})$ per ACK).
  • 3. Fast Recovery: Triggered by triple duplicate ACKs. Avoids dropping back to slow start.

7.4 Modern TCP Variations

  • TCP SACK (RFC 2018): Uses TCP header options to communicate discontinuous blocks of received data. Allows sender to retransmit all missing segments in a single RTT rather than just one.
  • TCP CUBIC: Uses a cubic function centered on time $K$ (when window size reaches prior peak $W_{\max}$). Grows quickly after backoff, slows down near $W_{\max}$, then probes aggressively beyond $W_{\max}$. Default algorithm in modern Linux.
  • Delay-Based Control (BBR): Monitors RTT and bottleneck delivery rate. Operates at the optimum point where the pipe is full ($BDP = \text{Bandwidth-Delay Product}$) without overflowing router buffers, avoiding bufferbloat.

7.5 TCP Fairness & Parallel Sockets

Two competing TCP connections sharing a bottleneck link converge to equal bandwidth shares ($R/2$) under identical RTTs due to the geometry of additive increase and multiplicative decrease. However:

  • Shorter RTT Bias: Connections with shorter RTTs ramp up window size faster than long-RTT connections.
  • Parallel Connections: An application opening $M$ parallel TCP sockets captures $M$ times more bandwidth share than an application using a single socket.
  • Unregulated UDP: UDP does not throttle back upon packet drops, potentially starving competing TCP traffic.

8. Evolution of Transport: QUIC & HTTP/3

Developed to overcome structural deficiencies in HTTP/1.1 and HTTP/2 over TCP.

8.1 Limitations of Classic TCP for Web Applications

  • Sequential Handshake Latency: TCP 3-way handshake (1 RTT) followed by TLS 1.2/1.3 cryptographic handshake (1–2 RTTs) incurs 2 to 3 RTT delays before any application data is transferred.
  • Head-of-Line (HoL) Blocking: Although HTTP/2 multiplexes multiple streams into one connection, TCP enforces a single strictly in-order byte stream. If one packet belonging to Stream 1 is lost, the operating system holds back packets for Streams 2 and 3 in the receive buffer until the missing packet is retransmitted.

8.2 QUIC Architecture Innovations

  • Encapsulated in UDP: Runs in user space over UDP (port 443), allowing instant deployment across existing Internet firewalls and NAT middleboxes without kernel modifications.
  • Integrated 1-RTT / 0-RTT Connection Establishment: Merges connection state, congestion control initialization, and TLS 1.3 cryptographic handshakes into a single round trip. Resumed connections can transfer data in 0 RTT.
  • Stream-Level Independent Recovery (Elimination of HoL Blocking): Each multiplexed application stream has independent sequence tracking. Dropping a packet in Stream 1 only stalls Stream 1; Streams 2 and 3 are delivered to the application without delay.
  • Connection Migration: Connections are identified by a 64-bit Connection ID (CID) rather than the 4-tuple IP/port, allowing a client to switch from Wi-Fi to cellular data seamlessly without restarting connections.
