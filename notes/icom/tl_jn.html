1. Transport Layer Overview & Services

The transport layer provides logical communication between application processes running on different end-hosts. It rests above the network layer and below the application layer.

Transport Layer vs. Network Layer

  • Network Layer: Provides logical communication between hosts (computer-to-computer) using IP addresses.
    Analogy: Postal service moving letters from building to building.
  • Transport Layer: Provides logical communication between processes (app-to-app) using port numbers. It breaks application messages into segments (sender) and reassembles them into messages (receiver).
    Analogy: The internal mailroom delivering letters directly to specific office rooms inside the building.

Standard Protocols & RFC Specifications

Protocol RFC & Year Connection Style Characteristics & Deployment
TCP (Transmission Control Protocol) RFC 793 (1981), RFC 9293 (08/2022) Connection-oriented Reliable, ordered byte-stream, flow & congestion control.
UDP (User Datagram Protocol) RFC 768 (1980) Connectionless Unreliable, unordered datagrams, minimal overhead (8-byte header).
SCTP (Stream Control Transmission Protocol) RFC 4960 (2007) Connection-oriented Multi-streaming, multi-homing. Limited deployment because legacy firewalls/NATs (middleboxes) fail to recognize the IP protocol number (132) and drop packets.
DCCP (Datagram Congestion Control Protocol) RFC 4340 (2006) Connection-oriented datagram Unreliable transmission with built-in congestion control. Limited deployment due to middlebox ossification (protocol number 33).
QUIC RFC 9000 (05/2021) Connection-oriented (over UDP) Implemented in user-space on top of UDP to bypass middlebox filtering; embeds TLS 1.3, achieves 0-RTT/1-RTT handshakes, eliminates Head-of-Line (HoL) blocking, and supports connection migration.

2. Multiplexing and Demultiplexing

Multiplexing (Sender): Gathering data from multiple application sockets, encapsulating data with transport layer headers, and passing segments to the network layer.

Demultiplexing (Receiver): Examining segment header fields (primarily port numbers and IP addresses) to deliver incoming segments to the appropriate application socket.

Connectionless Demultiplexing (UDP)

  • A UDP socket is identified solely by a 2-tuple: extUDPSocket=(extDestinationIPAddress, extDestinationPortNumber)
  • When an IP datagram arrives at a host, the host directs the UDP segment to the socket matching the destination port number, regardless of source IP or source port.
  • Source IP and source port are included in the UDP header so the receiving process can determine the return address.

Connection-Oriented Demultiplexing (TCP)

  • A TCP socket is identified by a 4-tuple: extTCPSocket=(extSourceIP, extSourcePort, extDestinationIP, extDestinationPort)
  • The receiving host uses all four values to route segments to the matching socket.
  • This design enables a server (e.g., Apache/Nginx listening on port 80/443) to support simultaneous TCP connections from thousands of clients, spawning dedicated client sockets for each distinct 4-tuple.

Multi-Layer Demultiplexing Hierarchy

  • Ethernet / Link Layer: Demultiplexes based on the Frame Type field (e.g., 0x0800 for IPv4, 0x0806 for ARP).
  • Network Layer (IP): Demultiplexes based on the Protocol ID field in the IPv4 header:
    • 6: TCP
    • 17: UDP
    • 33: DCCP
    • 132: SCTP
    • 1: ICMP, 2: IGMP
  • Transport Layer: Demultiplexes to specific application processes based on the Destination Port Number.

3. Connectionless Transport: UDP (RFC 768)

UDP is a minimal transport protocol that provides "best-effort" service without connection setup, state maintenance, or flow/congestion control.

Why Use UDP?

  1. No Connection Establishment Delay: Does not introduce a 3-way handshake round-trip time (RTT).
  2. No Connection State: Servers do not maintain state buffers, sequence numbers, or timers, allowing them to support many more active clients.
  3. Small Header Overhead: Fixed 8 bytes compared to TCP's minimum 20 bytes.
  4. Unregulated Sending Rate: Senders push data as fast as desired without being throttled by congestion control (ideal for real-time streaming).

UDP Segment Structure (8 Bytes Header)

Source Port # (16 bits)
Destination Port # (16 bits)
Length in Bytes (16 bits)
Header + Payload
Checksum (16 bits)
Error detection
Application Data (Payload)
Note on the Length Field
Although the IP header already contains a "Total Length" field, the UDP Length field provides modularity and self-containment for transport layer implementations.

UDP Checksum Calculation

Sender: Treats all 16-bit words of the pseudo-header (IP addresses, protocol), UDP header, and data as integers, computes their 1's complement sum, and inverts the bits to obtain the checksum.

Receiver: Adds all 16-bit words including the checksum. If no bits are flipped, the sum must be all 1s (0xFFFF). Any 0 indicates an error.

4. Principles of Reliable Data Transfer (rdt)

Because underlying network channels can corrupt packets (bit errors) or drop packets (loss), transport protocols implement reliable service abstraction using specific control mechanisms.

Fundamental ARQ Mechanisms

  • Error Detection: Checksums detect bit corruption in transmitted segments.
  • Receiver Feedback: Positive Acknowledgments (ACKs) and Negative Acknowledgments (NAKs).
  • Sequence Numbers: Distinguish new packets from duplicate retransmissions.
  • Timers & Retransmission: Recover from lost packets or lost ACKs when silence occurs.

5. Connection-Oriented Transport: TCP

TCP is a point-to-point, full-duplex, connection-oriented protocol providing reliable, in-order byte stream delivery with flow and congestion control.

TCP Segment Structure

Source Port # (16 bits)
Destination Port # (16 bits)
Sequence Number (32 bits) — byte offset of first data byte
Acknowledgment Number (32 bits) — next expected byte
Header Length (4 bits)
Flags (C, E, U, A, P, R, S, F)
Receive Window (16 bits) — Flow control (rwnd)
Internet Checksum (16 bits)
Urgent Data Pointer (16 bits)
Options (Variable Length: 0 to 40 bytes) — MSS, SACK, Window Scale
Application Data (Payload)

Header Size: Minimum is 20 bytes (Options = 0). Maximum is 60 bytes (4-bit Header Length field max value is 15imes4extbytes=60extbytes).

MTU vs. MSS

  • MTU (Maximum Transmission Unit): Largest IP packet link-layer frame can hold (typically 1500 bytes for standard Ethernet).
  • MSS (Maximum Segment Size): Maximum amount of application data inside a single TCP segment: extMSS=extMTU−extIPHeader(20bytes)−extTCPHeader(20bytes) For a link with MTU = 576 bytes: extMSS=576−20−20=536extbytes.

TCP Receiver ACK Generation Rules (RFC 5681)

Receiver Event TCP Receiver Action
Arrival of in-order segment with expected sequence number. All prior data already ACKed. Delayed ACK: Wait up to 500 ms for next segment. If no next segment arrives, send ACK.
Arrival of in-order segment with expected sequence number. One other segment has ACK pending. Immediate ACK: Immediately send a single cumulative ACK covering both in-order segments.
Arrival of out-of-order segment with higher-than-expected sequence number (Gap detected). Duplicate ACK: Immediately send duplicate ACK indicating the sequence number of next expected byte.
Arrival of segment that partially or completely fills gap. Immediate ACK: Immediately send cumulative ACK provided segment starts at lower end of gap.

TCP Flow Control

Prevents the sender from overflowing the receiver's application buffer.

  • Receiver advertises free buffer space using the receive window (rwnd) field: extrwnd=extRcvBuffer−(extLastByteRcvd−extLastByteRead)
  • The sender guarantees that in-flight unacknowledged data never exceeds extrwnd: extLastByteSent−extLastByteAcked≤extrwnd

TCP Connection Management

Three-Way Handshake (Connection Establishment)

  1. SYN (Client o Server): Client chooses initial sequence number x, sends SYN=1, Seq=x. Client state o SYN_SENT.
  2. SYN-ACK (Server o Client): Server allocates resources, chooses initial sequence number y, sends SYN=1, ACK=1, Seq=y, Ack=x+1. Server state o SYN_RCVD.
  3. ACK (Client o Server): Client sends ACK=1, Seq=x+1, Ack=y+1. May carry data. Client & Server state o ESTABLISHED.

Four-Way Handshake (Connection Teardown)

  1. Client o Server: Client sends FIN=1, Seq=u. Client state o FIN_WAIT_1.
  2. Server o Client: Server replies with ACK=1, Ack=u+1. Client state o FIN_WAIT_2; Server state o CLOSE_WAIT.
  3. Server o Client: When ready to terminate, server sends FIN=1, Seq=v. Server state o LAST_ACK.
  4. Client o Server: Client replies with ACK=1, Ack=v+1. Server state o CLOSED. Client enters TIME_WAIT (waits Math input errorMath input error) before entering CLOSED to ensure delayed packets clear the network.

6. Principles of Congestion Control

Congestion Control vs. Flow Control:

  • Flow Control: Point-to-point mechanism preventing one sender from overwhelming one receiver's buffer.
  • Congestion Control: Network-wide mechanism preventing many senders from overwhelming the switches and links in the network core.

Three Congestion Scenarios & Their Costs

Scenario Configuration Behavior & Manifestations Congestion Cost
Scenario 1 2 senders, 1 router, infinite buffers, capacity R. As λextinoR/2, queue grows infinitely, causing huge queueing delays. Throughput flattens at R/2. Extremely high delays as packet queues spiral out of control.
Scenario 2 2 senders, 1 router, finite buffers, capacity R. Packets drop when buffers are full. Senders must retransmit dropped packets. Premature timeouts cause unneeded duplicate transmissions. Wasted bandwidth carrying retransmissions and redundant duplicates; goodput drops well below R/2.
Scenario 3 4 senders, 4 routers, finite buffers, multi-hop paths. Packets dropped downstream waste all upstream transmission capacity and buffering already consumed. At heavy loads, throughput drops catastrophically to near 0. Congestion Collapse: Upstream capacity completely wasted on packets that never reach their destination.

End-to-End vs. Network-Assisted Congestion Control

Dimension End-to-End Congestion Control Network-Assisted Congestion Control
Router Role Passive/Silent; forwards packets only. Active; monitors queue depth and marks packets.
Detection Method Sender infers congestion from packet drops (timeout or triple duplicate ACKs) and RTT inflation. Direct feedback from routers using Explicit Congestion Notification (ECN in IP/TCP headers).
Pros & Cons Simple, keeps network core dumb and highly scalable; but reactive (loss must occur first). Proactive, avoids drops and wasted bandwidth; but requires complex router support across autonomous systems.

7. TCP Congestion Control Mechanisms

TCP dynamically regulates its transmission rate using the Congestion Window (cwnd):

Math input errorMath input error extLastByteSent−extLastByteAcked≤min(extcwnd, extrwnd)

AIMD (Additive Increase, Multiplicative Decrease)

  • Additive Increase: Increase cwnd by 1 MSS every RTT until loss occurs (probing for extra bandwidth).
  • Multiplicative Decrease: Cut cwnd in half on packet loss detected by 3 duplicate ACKs; reset cwnd to 1 MSS on loss detected by timeout.
  • Produces the famous TCP sawtooth throughput curve.

State Machine: Slow Start vs. Congestion Avoidance vs. Fast Recovery

  • Slow Start: Initial phase; extcwnd=1extMSS. Doubles every RTT (1o2o4o8o16…) by adding 1 MSS for every received ACK until extcwnd≥extssthresh.
  • Congestion Avoidance: Linear growth phase (extcwnd≥extssthresh). Increments extcwnd by 1extMSSimes(extMSS/extcwnd) per ACK (adding roughly 1 MSS per RTT).
  • Fast Retransmit & Fast Recovery (TCP Reno):
    1. Triggered upon receiving 3 duplicate ACKs.
    2. Set extssthresh=extcwnd/2.
    3. Retransmit missing segment immediately without waiting for timeout.
    4. Set extcwnd=extssthresh+3extMSS (accounting for the 3 segments that triggered the dup ACKs and left the pipe).
    5. For each additional duplicate ACK received, extcwnd=extcwnd+1extMSS.
    6. When new ACK arrives acknowledging the missing data, set extcwnd=extssthresh and return to Congestion Avoidance.

TCP Tahoe vs. TCP Reno

Loss Event TCP Tahoe TCP Reno
Triple Duplicate ACKs Sets extssthresh=extcwnd/2; cuts extcwnd=1extMSS; enters Slow Start. Sets extssthresh=extcwnd/2; sets extcwnd=extssthresh+3; enters Fast Recovery (skips Slow Start!).
Timeout Sets extssthresh=extcwnd/2; cuts extcwnd=1extMSS; enters Slow Start. Sets extssthresh=extcwnd/2; cuts extcwnd=1extMSS; enters Slow Start.

TCP SACK (Selective Acknowledgment - RFC 2018)

Standard Reno can only retransmit one lost segment per RTT. If multiple segments in a window are dropped, Reno suffers multiple window halving or timeouts. SACK allows the receiver to explicitly inform the sender of non-contiguous blocks received (e.g., ACK 1000, SACK 2000-3000, 4000-5000), allowing targeted retransmissions in a single RTT.

TCP CUBIC vs. Classic AIMD

Feature Classic TCP (AIMD / Reno) TCP CUBIC
Probing Function Linear increase (+1 MSS / RTT). Sluggish recovery in high-bandwidth long-delay (BDP) networks. Cubic S-curve: Fast recovery when far from Wextmax, plateaus near Wextmax, probes aggressively above it.
Window Metric Tied strictly to packet RTT counts. Real elapsed physical time (t) since last loss, independent of RTT.
RTT Fairness Short RTT flows unfairly grab bandwidth faster than long RTT flows. Independent of RTT; achieves excellent fairness between short-haul and long-haul connections.
Adoption Status Legacy; primarily educational. Default congestion control across Linux, Windows, macOS, Android.

8. Modern Transport Layer Evolution

Bufferbloat & Bottlenecks

Bottleneck Link: The lowest-capacity link along an end-to-end path that dictates maximum achievable throughput.

Bufferbloat: Router manufacturers historically added massive packet buffers to eliminate packet drops. However, loss-based congestion control protocols (Tahoe, Reno, CUBIC) keep filling buffers until a drop occurs, leading to enormous queueing delays (hundreds of milliseconds or seconds) without increasing throughput.

Delay-Based Congestion Control & Google BBR

Slide Typo Corrected: Definition of RTTextmin
Slide 22 described RTTextmin as "the min. throughput". This is incorrect: RTTextmin is the minimum physical Round-Trip Time (the two-way propagation delay when buffers along the path are empty).

Delay-Based Philosophy: "Keep the pipe just full, but not fuller." Instead of waiting for packet drops, monitor path delay variations:

  • Measure extRTTextmin during periods of no queueing.
  • Compute uncongested reference rate: Math input errorMath input error
  • If actual measured throughput matches the uncongested rate, linearly increase extcwnd. If observed RTT inflates significantly above extRTTextmin while throughput stays flat, queues are building up—throttle extcwnd before packet loss happens.
  • Google BBR (Bottleneck Bandwidth and RTT): A model-based algorithm that measures bottleneck bandwidth (extBtlBw) and two-way propagation delay (extRTprop) to operate at the Kleinrock optimal point (maximum throughput with minimum delay).

QUIC (Quick UDP Internet Connections - RFC 9000)

Engineered to solve transport ossification and head-of-line blocking in HTTP/2:

  • Runs over UDP in user-space: Bypasses rigid kernel updates and middlebox inspection that drop non-TCP packets.
  • 0-RTT / 1-RTT Handshake: Combines transport and cryptographic (TLS 1.3) handshakes into a single round trip.
  • Eliminates Head-of-Line (HoL) Blocking: Multiplexes independent streams. Packet loss on Stream A does not stall Stream B.
  • Connection Migration: Connections are identified by a 64-bit Connection ID rather than IP/port 4-tuple, enabling uninterrupted handoffs when switching networks (e.g., Wi-Fi to 5G).
