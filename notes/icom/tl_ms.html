1. Transport Core & Demultiplexing

  • Boundary: Network layer delivers between hosts (IP). Transport layer delivers between processes (ports).
  • UDP Demux (2-Tuple): (Dest IP, Dest Port). All datagrams with identical destination IP/port route to the same socket.
  • TCP Demux (4-Tuple): (Source IP, Source Port, Dest IP, Dest Port). Multi-client servers spawn dedicated sockets per unique 4-tuple.
  • Stack Protocol IDs: IP Header Protocol ID: 6 (TCP), 17 (UDP), 33 (DCCP), 132 (SCTP).

7. Transport Evolution & QUIC (HTTP/3)

Middlebox Bypassing

SCTP/DCCP failed because firewalls/NATs drop unrecognized protocol IDs. QUIC encapsulates inside UDP port 443 in user space, avoiding middlebox ossification.

1-RTT / 0-RTT Setup

TCP + TLS requires 2–3 serial round trips. QUIC merges transport connection parameters and TLS 1.3 crypto handshake into a single 1-RTT exchange (0-RTT on resumption).

No HoL Blocking

In HTTP/2 over TCP, dropping a packet in Stream 1 stalls all multiplexed streams. QUIC tracks stream sequence offsets independently so loss in Stream 1 never blocks Streams 2 and 3.

1. Transport Layer Services & Architecture

The transport layer establishes logical communication between application processes running on different hosts, abstracting away the complex multi-hop network mesh underneath.

1.1 Transport vs. Network Layer (Core Demarcation)

  • Network Layer: Logical communication between hosts (addressed by IP addresses).
  • Transport Layer: Logical communication between processes (identified by port numbers). Enhances best-effort network services with process-to-process multiplexing and optional reliability.
  • The Household Analogy:
    • Hosts: Houses (Ann's house and Bill's house).
    • Processes: 12 kids in each house.
    • Messages: Letters in envelopes.
    • Transport Protocol: Ann and Bill collecting and distributing mail to kids.
    • Network Protocol: Postal service delivering mail between houses.

1.2 Protocol Ecosystem & Middlebox Problem

  • TCP (RFC 793, RFC 9293): Connection-oriented, in-order reliable byte stream, flow control, congestion control.
  • UDP (RFC 768): Bare-bones, connectionless, unordered, best-effort datagram service.
  • SCTP & DCCP: Deployment failed across the global Internet due to middlebox ossification (firewalls drop unrecognized Layer 4 protocols).
  • Missing Guarantees: Standard IP transport protocols offer no delay/latency guarantees and no minimum throughput guarantees.

2. Multiplexing & Demultiplexing Mechanics

  • Multiplexing (Sender): Gathers data from application sockets, appends transport headers (ports), and passes segments down to the network layer.
  • Demultiplexing (Receiver): Inspects header fields to deliver segment payloads to the matching process socket.

2.1 Comparison: UDP vs. TCP Sockets

Protocol Socket Identifier Tuple Demultiplexing Policy
UDP 2-Tuple: (Dest IP, Dest Port) All arriving segments with the target destination IP and port are dumped into the same socket. Source IP and port serve only as return addresses.
TCP 4-Tuple: (Source IP, Source Port, Dest IP, Dest Port) The welcoming socket on port 80 listens for connections; each accepted client connection is instantiated into a dedicated socket tied to the full 4-tuple.

2.2 Demux Across Stack Protocol IDs

  • Link Layer Frame Header → IP Protocol ID (e.g., Ethernet Frame Type).
  • IP Header → Transport Layer: 6 for TCP, 17 for UDP, 33 for DCCP, 132 for SCTP.
  • Transport Header → Application Socket via 16-bit Port Numbers.

3. Connectionless Transport: UDP (RFC 768)

A lightweight protocol adding only port multiplexing and basic error checking to IP.

  • Design Benefits: Zero handshake delay (0 RTT), no endpoint connection state (highly scalable for servers), tiny 8-byte header, unthrottled transmission rate.
  • Use Cases: Real-time streaming/VoIP (loss-tolerant, rate-sensitive), DNS queries, SNMP, and HTTP/3 via QUIC.

3.2 One's Complement Checksum

Calculation: Sender treats all 16-bit words (header, data, IP pseudo-header) as integers and computes their sum with end-around carry. Inverts bits to store checksum. Receiver adds all words including checksum; result must be all 1s (0xFFFF) or error detected.

4.2 Pipelined Protocols (GBN vs. SR)

Pipelining keeps multiple packets in flight simultaneously: Usender=N⋅(L/R)RTT+(L/R)U_{\text{sender}} = \frac{N \cdot (L / R)}{RTT + (L / R)}Usender​=RTT+(L/R)N⋅(L/R)​.

  • Go-Back-N (GBN): Sender maintains window NNN; uses single timer for send_base. Cumulative ACKs. Receiver discards out-of-order packets and re-ACKs highest in-order. On timeout, sender retransmits entire window starting at send_base.
  • Selective Repeat (SR): Receiver buffers out-of-order packets. Sender maintains individual timers per packet and retransmits only the single unACKed packet on timeout.

5. Connection-Oriented Transport: TCP

5.1 Segment Format & Mechanics

  • Sequence Numbers: Byte-stream offset of the first data byte in payload.
  • ACK Numbers: Next expected byte sequence number (cumulative ACK).
  • Header Length (4 bits): Length in 32-bit words (min 20B, max 60B).
  • Flags: SYN, ACK, FIN, RST, PSH, URG, and ECN flags (ECE, CWR).
  • Receive Window (rwnd): Flow control buffer space advertised by receiver.

5.3 Fast Retransmit & Delayed ACKs (RFC 5681)

  • Delayed ACK: In-order segment arrives with all previous data ACKed: wait up to 500 ms for next segment. If another arrives, send cumulative ACK immediately.
  • Fast Retransmit: Receipt of 3 duplicate ACKs (4 identical ACKs total) triggers immediate retransmission of missing segment before timer timeout.

5.4 Handshake & TIME_WAIT (2×MSL2 \times \text{MSL}2×MSL)

  • Setup: 3-way handshake initializes sequence numbers and buffer variables.
  • Teardown: 4-way FIN/ACK handshake. Client remains in TIME_WAIT for 2×MSL2 \times \text{MSL}2×MSL (Maximum Segment Lifetime) to retransmit lost final ACKs and drain old lingering packets from the network.

6. Congestion Control Mechanics (AIMD to CUBIC & BBR)

  • Costs of Congestion: Exploding queue delays as λin→R/2\lambda_{\text{in}} \to R/2λin​→R/2, capacity wasted on retransmitting dropped packets, and upstream network capacity wasted when multi-hop packets drop downstream.
  • AIMD Principle: Additive increase (+1 MSS/RTT) probes for bandwidth; multiplicative decrease (cut in half on 3 dup ACKs, cut to 1 MSS on timeout) drives competing flows to efficiency and fairness.
  • Tahoe vs. Reno: Tahoe cuts to 1 MSS on 3 dup ACKs. Reno cuts ssthresh=cwnd/2\text{ssthresh} = \text{cwnd}/2ssthresh=cwnd/2, sets cwnd=ssthresh+3 MSS\text{cwnd} = \text{ssthresh} + 3\text{ MSS}cwnd=ssthresh+3 MSS (Fast Recovery), and returns directly to linear Congestion Avoidance upon a fresh ACK.
  • CUBIC: Modern Linux default. Uses a cubic window growth curve centered at inflection time KKK (Wmax⁡W_{\max}Wmax​).
  • Google BBR: Delay-based congestion control that measures Bottleneck Bandwidth and min RTT, avoiding router bufferbloat entirely.

7. Transport Evolution & QUIC (HTTP/3)

  • TCP/TLS Bottlenecks: 2–3 serial RTT handshakes; Head-of-Line (HoL) blocking where a single lost packet delays all multiplexed streams in the socket buffer.
  • QUIC Innovations: Runs in user space over UDP (port 443); combines transport and TLS 1.3 handshake into 1 RTT (0 RTT on resumption); eliminates HoL blocking by tracking streams independently at Layer 4; supports seamless connection migration via 64-bit Connection IDs.

Q1. Why is SCTP and DCCP deployment limited in the Internet?

Answer: SCTP and DCCP suffer from middlebox ossification. Existing firewalls and NAT routers deployed across the Internet only understand TCP (protocol 6) and UDP (protocol 17). Because middleboxes cannot inspect SCTP (protocol 132) or DCCP (protocol 33) headers, they drop these packets, preventing adoption on the public Internet.

Key Takeaway: New Layer 4 protocols must encapsulate inside UDP to bypass legacy middlebox restrictions.
ExplicitSlide 4

Q2. Why was QUIC designed on top of UDP?

Answer: By encapsulating inside UDP, QUIC avoids middlebox drops and operating system kernel upgrade delays. Firewalls already permit UDP on port 443, allowing QUIC to implement connection setup, encryption, and congestion control completely in user space.

Key Takeaway: UDP acts as an application-level substrate through intermediate firewalls and NATs.
Inferred CoreSlide 5

Q3. What is the fundamental difference between network layer and transport layer communication?

Answer: The network layer provides logical communication between hosts (IP addresses), whereas the transport layer provides logical communication between processes (port numbers). In the household analogy: houses are hosts, children in houses are processes, letters are messages, Ann & Bill are the transport protocol, and the postal service is the network layer.

ExplicitSlide 12 – 13

Q4. How does the transport layer know to deliver an arriving message to Firefox rather than Netflix or Skype?

Answer: Through demultiplexing using the Destination Port Number in the segment header. The client OS assigns an ephemeral port to the Firefox socket during request creation. The server echoes this port back in the Destination Port field, allowing the OS to route the payload to Firefox's socket.

Inferred CoreSlide 18 – 21

Q5. Why does TCP demux require a 4-tuple, whereas UDP requires only a 2-tuple?

Answer: UDP is stateless: all datagrams sharing the destination IP and port are placed in the same socket regardless of source. TCP is connection-oriented and tracks sequence numbers and buffers per connection; therefore, a server must separate concurrent clients on the same port into dedicated sockets identified by the full 4-tuple (Source IP, Source Port, Dest IP, Dest Port).

ExplicitSlide 24

Q6. Why is there a UDP? What are its primary design advantages?

Answer: UDP provides: 1) Zero connection establishment delay (0 RTT), 2) No endpoint connection state (high server concurrency), 3) Small fixed 8-byte header overhead, and 4) No congestion control throttling, allowing applications to transmit at their own designated pace.

Q7. How large should a UDP segment be?

Answer: Theoretically up to 65,535 bytes65,535\text{ bytes}65,535 bytes (bounded by the 16-bit Length field). In practice, segments are kept below the link MTU (typically 1500 bytes on Ethernet) to avoid IP-layer fragmentation and reassembly overhead.

ExplicitSlide 29

Q8. Is the length field in the UDP header strictly necessary?

Answer: Conceptually no, because total segment length can be derived from the IP Total Length minus IP Header Length. Technically yes, RFC 768 mandates the field to maintain protocol independence and fixed header structure.

Inferred CoreSlide 30 – 31

Q9. How does the UDP checksum calculate and detect bit errors?

Answer: The sender treats all 16-bit words as integers, sums them with 1's complement end-around carry, inverts the bits, and stores the result in the Checksum field. The receiver sums all 16-bit words including the checksum; a result of all 1s (0xFFFF) confirms no detected errors.

ExplicitSlide 38

Q10. In a stop-and-wait protocol, do we need sequence numbers in data packets?

Answer: Yes. Without a sequence number, if an ACK is delayed or lost and the sender retransmits, the receiver cannot determine whether the packet is a duplicate or new data. A 1-bit alternating sequence number (000 or 111) solves this.

ExplicitSlide 38

Q11. In a stop-and-wait protocol, do we need sequence numbers in ACK packets?

Answer: Yes. Sequence numbers in ACKs allow the sender to verify exactly which transmitted packet is being acknowledged, preventing confusion from delayed ACKs.

ExplicitSlide 38

Q12. Can we use a single type of ACK in reliable data transfer protocols?

Answer: Yes. By including the sequence number in the ACK, positive ACKs alone handle retransmission. Duplicate ACKs implicitly communicate packet loss without needing negative acknowledgments (NAKs).

Q13. In pipelined data transfer, which window/pipe size should be selected?

Q14. How do Go-Back-N (GBN) and Selective Repeat (SR) differ in buffering and timers?

Answer: GBN uses cumulative ACKs, a single timer for the oldest unACKed packet, and no receiver buffering (out-of-order packets are discarded; entire window is retransmitted on timeout). Q18. Why must TCP ignore retransmissions when estimating SampleRTT? (Acknowledgment Ambiguity)

Answer: Under Karn's Algorithm, when an ACK arrives for a retransmitted packet, the sender cannot tell whether it acknowledges the original transmission or the retransmission. Sampling retransmissions severely skews RTT estimates; therefore, TCP measures SampleRTT only for segments sent once.

Q20. Why must the TCP client enter the TIME_WAIT state for 2×MSL2 \times \text{MSL}2×MSL?

Answer: 1) To gracefully close the connection: if the client's final ACK is lost, the server retransmits its FIN, which the client can still ACK in TIME_WAIT. 2) To let lingering duplicate packets expire, preventing them from corrupting future connections reusing the same port numbers.

Q21. What happens to throughput and delay as packet arrival rate approaches link capacity R/2R/2R/2?

ExplicitSlide 75

Q22. What happens as sending rate increases in a multi-hop congested network?

Answer: Aggressive flows starve competing traffic sharing downstream bottlenecks, driving competing throughput to zero. Furthermore, when a packet is dropped downstream, all upstream transmission capacity and buffer memory used by that packet are completely wasted.

Additive increase probes with slope 1, while multiplicative decrease cuts rates proportionally, driving convergence toward the fairness line.

Q27. How does delay-based congestion control (e.g., Google BBR) eliminate bufferbloat?

Answer: Loss-based TCP fills router buffers until packets drop, causing bufferbloat delays. Delay-based congestion control compares measured throughput against uncongested throughput (cwnd/RTTmin⁡{\text{cwnd}}/{\text{RTT}_{\min}}cwnd/RTTmin​). If RTT rises while throughput plateaus, it reduces window size before loss occurs, keeping the pipe full without filling buffers.

Q28. Is TCP fair? Under what conditions does fairness hold?

Answer: Yes, under idealized conditions: all sessions share the same RTT, session count is fixed, and all run in Congestion Avoidance. In practice, flows with shorter RTTs ramp window sizes faster, capturing an unfair share of bandwidth.

Q30. Why is QUIC connection establishment faster than standard TCP + TLS?

Q31. How does QUIC eliminate transport Head-of-Line (HoL) blocking?

Answer: In HTTP/2 over TCP, all streams share one byte stream; a single lost packet blocks all streams in the receive buffer. QUIC provides independent stream-level sequencing at Layer 4: a dropped packet in Stream 1 pauses only Stream 1, allowing Streams 2 and 3 to be delivered to the application immediately.
